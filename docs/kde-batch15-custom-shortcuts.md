# Batch 15: native application and custom command shortcuts

This adapter stages native KDE application-component registration and custom command definitions until Apply. Revert reloads the current native state. The persistent `CustomShortcutsSettings` session owns its backend and survives page changes. Command creation, editing, deletion, registration, and application-component removal perform native readback; no command is executed by the adapter or its probe.

## Exact source contract

The audited installed target is Plasma Desktop **6.6.6**, kglobalacceld **6.6.5**, and KF6 KGlobalAccel SDK/runtime **6.24.0**. These package versions and `/usr/include/KF6/KGlobalAccel/kglobalaccel_version.h` were independently rechecked on 2026-10-17. Production discovery verifies installed package versions, the pinned bus-owner PID/UID, and protected package-owned native executable/library paths through bounded read-only checks. Both standalone kglobalacceld and KWin 6.6.6 Wayland embedding are supported. The embedded route requires `org.kde.KWin` and `org.kde.kglobalaccel` to share the same unique owner/PID, an exact KWin 6.6.6 Wayland `supportInformation` result, `kwin-wayland` 6.6.6, and the independently versioned `libkglobalacceld0` 6.6.5 package/library. Unsupported targets remain discoverable and read-only. Isolated test options bypass package checks only; they never use live paths or a live bus.

Read-only live diagnosis found both services at owner `:1.15`, PID `1779`, with KWin 6.6.6 Wayland. The process has `CAP_SYS_NICE`; even an unrestricted same-user `/proc/1779/exe` or `maps` read is denied. The embedded route therefore also accepts readable process `comm`/`cmdline` evidence for `/usr/bin/kwin_wayland`, together with the owner/version checks and protected package path. This is an explicit process-executable attestation limitation; the code does not claim it inspected the inaccessible executable link or loaded memory mappings. Installed ELF linkage was independently checked read-only: KWin links `libKGlobalAccelD.so.0`, provided by `libkglobalacceld0` 6.6.5. The standalone route still requires its actual `/proc/PID/exe` target.

- [Plasma Desktop v6.6.6 kcm_keys.cpp](https://github.com/KDE/plasma-desktop/blob/v6.6.6/kcms/keys/kcm_keys.cpp), `addCommand`, `editCommand`, and `quoteUrl`: native command definitions use `Type=Application`, `NoDisplay=true`, `StartupNotify=false`, and `X-KDE-GlobalAccel-CommandShortcut=true`. Literal percent signs use native `%%` normalization. Local file URLs become a quoted local executable path; a path containing spaces remains one argument. New identities use `net.local.<UUID>.desktop` to avoid guessing executable-derived IDs. Edits retain unknown desktop fields.
- [KF6 v6.24.0 root D-Bus XML](https://github.com/KDE/kglobalaccel/blob/v6.24.0/src/org.kde.KGlobalAccel.xml) and [component XML](https://github.com/KDE/kglobalaccel/blob/v6.24.0/src/org.kde.kglobalaccel.Component.xml): exact method arity and types are checked for `allComponents`, `getComponent`, `doRegister`, `unregister`, v2 key getters, contexts, metadata, read-only `Properties.Get(Component, uniqueName)` identity, and `cleanUp`. The exported string identity resolves even entirely actionless components; complete typed context inventories participate in snapshot hashes and Apply guards. Full four-chord alternatives come from the v2 `a(ai)` getters; metadata's legacy integer lists are insufficient.
- [kglobalacceld v6.6.5 kserviceactioncomponent.cpp](https://github.com/KDE/kglobalacceld/blob/v6.6.5/src/kserviceactioncomponent.cpp): registered service actions and `_launch` use desktop definitions and their native defaults. Persistent `.desktop` bindings live under `[services][component.desktop]`; values equal to defaults have no override. The adapter preserves saved bindings when editing a definition and verifies cleanup persistence.
- [kglobalacceld v6.6.5 component.cpp](https://github.com/KDE/kglobalacceld/blob/v6.6.5/src/component.cpp), `cleanUp`: cleanup operates on `_current->_actionsMap`. `KServiceActionComponent::cleanUp` marks default-context shortcuts absent and delegates. That single call alone does not guarantee whole-component removal with additional contexts. Batch 16 closes this gap with context-qualified root `unregister(component|context, action)`: `GlobalShortcut::unRegister` delegates to `Component::unregisterShortcut`, which deletes the action name from every context. The complete context and action inventory, including empty contexts, is preserved and guarded without activating a context.
- [kglobalacceld v6.6.5 globalshortcutsregistry.cpp](https://github.com/KDE/kglobalacceld/blob/v6.6.5/src/globalshortcutsregistry.cpp) and [kglobalacceld.cpp](https://github.com/KDE/kglobalacceld/blob/v6.6.5/src/kglobalacceld.cpp): new `doRegister` service creation calls `loadFromService`, rather than `loadSettings`. Saved overrides on an unregistered identity would therefore be ignored. Such registrations are refused before any mutation, preserving the saved bytes. Declared defaults conflicting with existing keys are also refused before registration; the adapter never steals occupied keys. Service registration and persistence belong to the daemon. Existing service resolution may depend on native KSycoca refresh. This adapter does not run a cache builder, reload a service, activate a context, or invoke a shortcut.

## Discovery and ownership

Discovery reads an explicit recursive XDG desktop-file catalog using per-file `KDesktopFile`/`KService` parsing. It never queries `KApplicationTrader`, `serviceByStorageId`, or `KSycoca`. User directories take priority; a user `Hidden=true` tombstone reserves its ID and hides lower-priority copies. Nested desktop IDs use the native slash-to-dash form. Applications and desktop actions are not restricted to a product-owned allowlist. Invalid, oversized, unreadable, dangling-link, and unsupported-type optional definitions stay outside the picker while reserving their IDs. Their directory-entry metadata, link target, target presence/metadata, and readability are fingerprinted consistently in both discovery and Apply guards. A single broken optional launcher does not disable the manager; target appearance or other catalog changes still stop Apply.

Existing native KCM-created command files are editable when they have the KDE command marker, reside directly in the user applications directory, are user-owned regular files with one hard link, and pass directory, permissions, and immutable-policy checks. They do not need an app-specific marker. System, linked, missing, and protected definitions remain visible where the daemon reports them, with a read-only reason. A command shadowing another installed file may be edited but cannot be deleted because deletion would expose the other file.

An existing saved command without a registered component can be explicitly registered, edited, or deleted. File-only deletion does not call native cleanup for a nonexistent component. Application-component removal keeps the installed application file. Deleting a command removes only its verified user command file and its registered component; arbitrary application desktop files are never deleted.

## Apply, races, and recovery

Workers capture values and shared transports; GUI objects are never accessed by the native worker. Every production D-Bus call has a two-second timeout. Read and write operations have aggregate budgets, size limits, bounded native-persistence polling, and operation tokens. Session signals reject stale tokens and wrong phases. File watches debounce reloads; a foreign reload preserves a dirty draft and blocks Apply until Revert.

Apply independently rereads the pinned daemon owner, exact native interface, catalog identities, policy, saved bindings, and configuration baseline before changing anything. Private temporary desktop files prepare edits. Directory descriptors use `O_NOFOLLOW`; replacement uses checked file identities, a private `O_EXCL` temporary file, `fsync`, and descriptor-relative rename/unlink. The backend compares the entire relevant desktop catalog and untouched native configuration/registry around mutations. Existing unknown config and desktop fields are preserved.

Before native mutation, failures roll back only committed bytes whose identity still matches this operation's own result. Foreign edits are never overwritten during rollback. A failed rollback or known partially completed native operation reports Partial and preserves the draft. Revert can recover a known partial result by loading a complete fresh baseline. A timed-out or malformed native mutation reply reports Uncertain and locks further writes for that bus owner, even across Refresh/Revert; a new owner releases the lock. False success fails controller-side verification of requested definitions, complete registration actions/defaults, removals, unchanged definitions/bindings, and daemon identity.

Command edits persist the definition, but the existing daemon component retains its original parsed service until component recreation or a service/session restart. A cache rebuild alone does not replace that service object. The UI explicitly communicates this limitation. No restart or cache rebuild is performed automatically. Scheme imports stage multiple command definitions atomically through `stageCommands`; any invalid, duplicate, protected, application-conflicting, or removed identity leaves the whole prior draft intact. New command binding imports still require Apply followed by Global Shortcuts refresh and explicit binding staging; automatic deferred binding import is an unresolved goal.

## Batch 16: whole-component removal and command-adoption audit

The integrated Batch 16 run passed all 72 suites, including the combined native
edit-and-registration and complete-context removal fixtures. Read-only live
discovery and its 26-path unchanged-fingerprint evidence are recorded in
[Batch 16 validation](kde-batch16-shortcut-imports.md#verification); no live
removal, invocation or execution-adoption acceptance is claimed.

Multi-context removal enumerates all contexts and action names, unregisters nondefault-only names first, then names with default-context siblings. Each call uses an explicit known `component|context` identity; one successful unregister deletes siblings bearing that action name from every context. After each mutation the backend verifies the exact remaining action inventory, unchanged context/object-path identities while the component exists, and untouched components/configuration/files. Native disappearance during the sequence is reconciled as the intended complete deletion. No context activation or active-context restoration is performed.

[kglobalacceld v6.6.5 globalshortcutsregistry.cpp](https://github.com/KDE/kglobalacceld/blob/v6.6.5/src/globalshortcutsregistry.cpp), `writeSettings`, deletes the complete component and saved group when its default-context action map is empty. Root unregister schedules that writer after 500 ms. Thus nondefault-only and empty contexts are also destroyed. For a completely actionless registered component, the adapter verifies a transient keyless empty default dummy, unregisters it to schedule the native writer, then waits for complete component/context/config-group absence. Normal default-only services retain the KCM `cleanUp` path. Timed-out replies lock the owner; incomplete pruning reports Partial. New context/action inventories and immutable empty-context policy block stale or protected writes. Application files remain installed; only verified user command files are deleted.

The public XML exports context enumeration and activation but no active-context-name getter. Inferring the active context from `isActive`, `actionList`, or `allActionsForComponent` is incomplete for empty contexts and keyless actions. The unregister protocol avoids that missing API entirely. It also avoids trying to reconstruct an unknown active context after a partial cleanup.

Edited command adoption was audited through the actual trigger chain, rather than inferred from the presence of a cached pointer. [kglobalacceld v6.6.5 kserviceactioncomponent.cpp](https://github.com/KDE/kglobalacceld/blob/v6.6.5/src/kserviceactioncomponent.cpp), `emitGlobalShortcutEvent`, passes its stored service to `ApplicationLauncherJob` for `_launch`; desktop actions come from the same stored service. [KF6 KIO v6.24.0 applicationlauncherjob.cpp](https://github.com/KDE/kio/blob/v6.24.0/src/gui/applicationlauncherjob.cpp) retains that pointer and passes it to `KProcessRunner::fromApplication`. [kprocessrunner.cpp](https://github.com/KDE/kio/blob/v6.24.0/src/gui/kprocessrunner.cpp) constructs `DesktopExecParser` from the supplied service; [desktopexecparser.cpp](https://github.com/KDE/kio/blob/v6.24.0/src/core/desktopexecparser.cpp), `resultingArguments`, reads `service.exec()`. [KService v6.24.0 kservice.cpp](https://github.com/KDE/kservice/blob/v6.24.0/src/services/kservice.cpp), `exec`, returns the stored string. This path does not reread the command desktop definition on each trigger.

The registry's `databaseChanged` handler checks whether existing services still exist and keeps them; discovery skips IDs already registered. Neither path replaces the retained service for an edited existing command. `doRegister` on an existing component can update friendly labels but cannot change that retained Exec. The exact public XML has no per-component definition reload or runtime Exec getter. Component removal/recreation could adopt a new service and restore bindings, but arbitrary nondefault active context cannot be restored through a getter, and a label-only readback would not prove runtime Exec adoption. This adapter continues to report persistent definition saving separately from execution adoption and performs no cache rebuild, daemon restart, context activation, or shortcut invocation to make that claim.

Added private fixtures cover distinct names shared across contexts, nondefault-only actions, entirely actionless components, empty-context policy, typed context races, foreign config during partial unregister, uncertain replies, and incomplete native pruning. The read-only probe reports the complete typed context inventory. Root remains the sole builder; no live mutation or command invocation was used for this audit.
